# ADR-0016: Hosting and Infrastructure Topology

## Status
Accepted — 2026-08-10

## Context
The canonical stack fixes the major hosting components — Vercel for the Next.js app, a managed Postgres provider (Neon *or* Supabase, concrete choice deferred to this ADR), and Cloudflare for Stream/R2/CDN — but leaves open: which managed Postgres provider specifically, how infrastructure is provisioned and versioned, what the environment topology looks like end-to-end (not just app-level, which ADR-0015 covers for CI/branching), how secrets are managed across three third-party platforms, and what disaster-recovery posture is appropriate for a platform that — while not monetized — holds real volunteer PII, GDPR-regulated consent/DSAR records, grant-reporting hour data, and is expected to run at commercial-grade reliability per this project's stated bar.

ADR-0015 (Testing and CI/CD Strategy) already commits to **per-PR Neon branch databases** as the preview-environment mechanism, using Neon's copy-on-write branching to give every PR an isolated, real Postgres instance cheaply. That commitment is a strong input to this ADR: Supabase does not offer equivalent lightweight database branching (its branching feature, where available, provisions a fuller project stack per branch and is significantly more expensive to run per-PR), while Neon's branching is exactly the copy-on-write, seconds-to-create, cents-to-run primitive the CI strategy depends on.

The project also needs Supabase Auth per the canonical auth decision (Supabase Auth + JWT + httpOnly cookie sessions) — but "use Supabase Auth" does not require "use Supabase Postgres." Supabase Auth can run against any Postgres via its GoTrue service pointed at an external database connection string, and Supabase explicitly supports this "bring your own database" pattern for its auth product independent of hosting the primary database on Supabase's platform.

## Decision
**Neon** is the managed Postgres provider for all environments. **Supabase Auth** (GoTrue) is used purely as the authentication service, configured to issue JWTs validated against the application's own Neon-hosted `identity` schema for role/scope data — Supabase's own Postgres product is not used; Supabase Auth is deployed pointing at the Neon connection string as its user store is not required here since `identity.users` is the source of truth and Supabase Auth's own `auth.users` table is treated as a thin credential/session store synced via webhook on signup, not duplicated business data.

**Vercel** hosts the Next.js application (App Router) across all environments, with the background worker (graphile-worker) running as a **separate long-lived Node process on Fly.io** rather than on Vercel — Vercel's serverless functions are not designed for long-running polling workers, and graphile-worker needs a persistent process holding a Postgres connection pool and `LISTEN/NOTIFY` subscription.

**Cloudflare** provides Stream (video), R2 (object storage: DSAR export bundles, profile photos, moderation evidence attachments), and CDN/DNS, one Cloudflare account with per-environment resource separation (see topology below).

**Terraform** is the infrastructure-as-code tool for all of the above, using the official `vercel/vercel`, `kreuzwerker/docker`-adjacent Fly.io community provider (`fly-apps/flyctl` wrapped via a Terraform `null_resource` + `local-exec` where no first-party provider exists, or the `fly-apps/terraform-provider-fly` community provider where sufficiently mature — the CI-friendly non-first-party-provider parts are the accepted trade-off of using Fly.io, see Consequences), `cloudflare/cloudflare`, and `github` (for branch protection per ADR-0015) providers, with Neon provisioned via the `kislerdm/neon` community Terraform provider.

### Environment topology
| Environment | Vercel | Postgres (Neon) | Worker (Fly.io) | Cloudflare |
|---|---|---|---|---|
| **Production** | `main` branch, production domain | Neon production project, primary branch, autoscaling compute | `agentics-worker-prod` app, 2 machines (HA) | Production Stream/R2 buckets, production zone |
| **Staging** | `staging` branch, `staging.volunteer.agentics.org` | Neon staging project (separate Neon *project*, not just a branch, for full isolation of billing/compute/backup policy) | `agentics-worker-staging` app, 1 machine | Separate Stream/R2 buckets (`-staging` suffix), staging subdomain zone |
| **Preview (per-PR)** | Vercel preview deployment, auto-generated URL | Neon branch, created from **staging** project as parent (copy-on-write, seconds to provision), auto-deleted on PR close | Not deployed — preview e2e-smoke tests run graphile-worker in-process via testcontainers per ADR-0015, not against a live Fly.io worker | Shared staging Stream/R2 buckets, scoped by an environment-prefixed object key (`preview-{pr}-...`) to avoid needing per-PR Cloudflare resources |

Production and staging are fully separate Neon *projects* (not branches of one project) so that production's backup policy, compute autoscaling limits, and IP allowlisting are independently configured and staging activity can never contend for production compute or accidentally share a connection pool. Preview branches off staging (never off production) so preview environments only ever see synthetic seed data, consistent with ADR-0014's no-real-PII-in-non-production stance.

### Secrets management
- **Vercel Environment Variables**, scoped per Vercel environment (Production / Preview / Development), is the source of truth for secrets consumed by the Next.js app at build/runtime — `DATABASE_URL`, `SUPABASE_AUTH_JWT_SECRET`, `RESEND_API_KEY`, `CLOUDFLARE_STREAM_TOKEN`, `SENTRY_DSN`. Managed via Terraform (`vercel_project_environment_variable` resource) so secret *keys* and their environment scoping are version-controlled even though values are not (Terraform state for these resources uses `sensitive = true` and values are sourced from a separate secrets store, not hardcoded in `.tf` files).
- **Actual secret values** live in **1Password** (already the org's password manager per standard nonprofit tooling) accessed via the 1Password Terraform provider and the 1Password CLI in CI (`op run -- terraform apply`), so no secret value is ever committed to a `.tf` file, a GitHub Actions YAML file, or a `.env` file in the repo. GitHub Actions secrets used for CI-only credentials (Vercel deploy token, Terraform Cloud token) are stored as encrypted GitHub Actions repository secrets, rotated quarterly.
- **Fly.io** secrets (`DATABASE_URL` for the worker, `GRAPHILE_WORKER_SCHEMA`) are set via `flyctl secrets set`, sourced from the same 1Password vault, applied through a Terraform `local-exec` provisioner tied to the Fly app resource so a `terraform apply` is still the single deploy path even though Fly's own Terraform provider support for secrets is limited.
- No secret is ever logged; the structured JSON logging setup (Sentry/OpenTelemetry per the canonical stack) has a redaction middleware stripping any log field matching a `SECRET|TOKEN|KEY|PASSWORD` name pattern before it leaves the process.

### Disaster recovery / backup policy
- **Postgres (Neon) point-in-time recovery**: production project configured with Neon's PITR at **7-day retention** (Neon's history retention on the production branch), giving recovery to any point within the trailing week — sized against this platform's risk profile (a GDPR erasure bug or a bad migration is the realistic worst case, not multi-week-old corruption going undetected). Staging PITR retention is 1 day (cost control; staging data is synthetic and reproducible from seed scripts).
- **Logical backups**: nightly `pg_dump` of the production database to a Cloudflare R2 bucket (`agentics-db-backups-prod`, versioned, with a 90-day object lifecycle before transition to R2 infrequent-access-equivalent storage class and eventual deletion at 1 year) via a scheduled Fly.io Machine (cron-style, using Fly's `flyctl machine run` with a schedule) — independent of Neon's own PITR, so a full provider-level Neon incident does not leave the platform with zero recovery path.
- **Backup testing cadence**: a quarterly **restore drill** — the most recent nightly `pg_dump` is restored into a fresh, throwaway Neon branch and the application's integration test suite (per ADR-0015) is run against it as a correctness check that the backup is actually restorable and structurally valid, not just that the file exists. This is a scheduled GitHub Actions workflow (`.github/workflows/dr-drill.yml`, `schedule: cron('0 6 1 */3 *')`) that posts its pass/fail result to the team's incident channel; a failed drill is treated as a P2 incident requiring same-week remediation, not a backlog item.
- **Recovery Point Objective (RPO)**: ≤ 24 hours via nightly logical backup as the floor, ≤ 5 minutes via Neon PITR as the practical target for any incident caught within the 7-day PITR window.
- **Recovery Time Objective (RTO)**: 4 hours for a full production restore from logical backup (documented runbook: provision fresh Neon project via Terraform, restore `pg_dump`, repoint Vercel/Fly `DATABASE_URL` secrets, redeploy) — this number has not yet been empirically validated by a full-restore drill at time of writing and the first quarterly drill's actual duration becomes the baseline RTO figure going forward.
- Cloudflare R2 (video source assets are held by Cloudflare Stream itself, not R2, and Stream's own storage is Cloudflare-managed and outside this backup policy's scope) — objects in R2 (DSAR exports, profile photos, moderation evidence) are lower-criticality and covered by R2's standard durability (11 nines) with no separate backup process, since these are either regeneratable (exports) or non-critical-if-lost-and-replaceable-by-the-user (photos).

## Consequences
### Positive
- Neon's branching model directly powers both the DR restore-drill process (throwaway branch from a backup) and the CI preview-environment strategy from ADR-0015 — one capability serving two needs, rather than building bespoke tooling for each.
- Fully separate Neon projects per environment (not just branches) means a staging incident (bad migration, runaway query) cannot degrade production compute or connection pool capacity.
- Terraform-everything means the full topology — Vercel projects, Cloudflare zones/buckets, Neon projects, Fly apps, GitHub branch protection — is reconstructable from version-controlled code, not tribal knowledge or manual console clicks, which matters for a small team without dedicated ops staff.
- Running Supabase Auth against Neon rather than adopting Supabase's full Postgres product avoids a second managed-Postgres relationship and keeps exactly one database vendor in the critical path, simplifying the DR story to "one database provider to restore."

### Negative / Trade-offs
- Using Supabase Auth pointed at an external (Neon) database is a less common configuration than Supabase's default all-in-one setup, and some Supabase dashboard conveniences (built-in table editor against `auth.users` alongside app tables in one project view) are unavailable — accepted because the auth/data-hosting decoupling is deliberate and the operational surface (JWT issuance, session management) Supabase Auth exposes doesn't require its dashboard's data browsing features for this use case.
- Running graphile-worker on Fly.io introduces a third infrastructure platform (beyond Vercel and Cloudflare) with its own deploy mechanism, secrets store, and — as noted above — a less mature Terraform provider than Vercel/Cloudflare/Neon, meaning some of the worker's infra is provisioned via `local-exec`/`flyctl` shell-outs rather than pure declarative Terraform resources. This is a known rough edge, accepted because no viable alternative keeps a persistent polling worker process on Vercel's serverless model.
- Nightly logical backups plus Neon PITR is a deliberately duplicated backup mechanism (belt-and-suspenders) with a real cost: the R2 backup bucket storage cost and the quarterly drill's engineering time. Accepted given this platform holds regulated PII and grant-reporting data where "the managed provider's built-in feature was enough" is not an acceptable answer if that provider has an outage or account-level incident.
- The RTO figure (4 hours) is currently an engineering estimate, not an empirically validated number — flagged explicitly above as needing correction after the first real drill, rather than presented as more certain than it is.

## Alternatives Considered
- **Supabase for both Postgres hosting and Auth (fully unified Supabase project).** Rejected as the primary database despite being one of the two canonically-allowed choices, specifically because ADR-0015's CI/preview-environment strategy depends on cheap, fast, copy-on-write database branching per PR, which is a Neon strength Supabase does not match at comparable cost/speed — Supabase branching (where offered) provisions more of a full project per branch, materially more expensive to run at PR volume. Auth is still taken from Supabase because it's the canonically fixed choice and GoTrue's external-database support is a first-class, documented configuration.
- **Self-hosted Postgres on a VM (e.g., a single Fly.io Postgres cluster or a DigitalOcean managed instance) instead of Neon.** Rejected: this is a small team explicitly avoiding dedicated ops staff (per the research's recommended-stack framing); self-managing Postgres HA, PITR, and failover is exactly the operational burden managed Postgres exists to remove, and neither Neon nor Supabase's pricing at this project's expected scale justifies the ops cost of self-hosting.
- **Running graphile-worker as a Vercel Cron-triggered serverless function (polling on a schedule) instead of a persistent Fly.io process.** Rejected: graphile-worker's design (LISTEN/NOTIFY for low-latency job pickup, long-lived connection pooling, in-process job concurrency control) is fundamentally a persistent-process model; forcing it into short-lived serverless invocations on a cron would mean losing low-latency job pickup (falling back to poll-only) and re-establishing a DB connection pool on every cold invocation, which is both slower and harder on Neon's connection limits than one persistent worker.
- **AWS (RDS + ECS/Fargate + S3 + CloudFront) as a single-vendor alternative to the Vercel/Neon/Cloudflare/Fly split.** Rejected: substantially more infrastructure surface and IAM/networking complexity for a small team to own, and abandons the specific managed-service strengths (Vercel's Next.js-native deploy pipeline, Cloudflare Stream's purpose-built video product, Neon's branching) the canonical stack was chosen for in the first place. A multi-vendor best-of-breed approach with Terraform tying it together is judged lower total operational burden than a single IaaS vendor requiring more manual assembly.

## Implementation Notes
- Terraform root modules: `infra/environments/{production,staging}/main.tf`, each composing shared modules from `infra/modules/{vercel-project,neon-project,cloudflare-stack,fly-worker}`. Preview-environment Neon branching is *not* Terraform-managed (it's ephemeral, per-PR, and driven by the `neondatabase/create-branch-action` GitHub Action per ADR-0015) — Terraform owns only the persistent staging/production infrastructure.
- `infra/modules/neon-project/main.tf` uses the `kislerdm/neon` provider's `neon_project` resource with `history_retention_seconds = 604800` (7 days) for production, `86400` (1 day) for staging, and a `neon_branch` resource for each project's default branch with autoscaling `min_cu`/`max_cu` set per environment (production: 0.5–4 CU autoscaling; staging: fixed 0.25 CU to control cost).
- Fly.io worker app: `infra/modules/fly-worker/fly.toml` template with `[processes] worker = "node dist/worker.js"`, `min_machines_running = 2` for production (HA — graphile-worker supports multiple concurrent worker processes safely via its job-locking design), `1` for staging.
- Nightly backup job: `infra/modules/fly-worker/backup-machine.toml`, a separate Fly Machine scheduled via `flyctl machine run --schedule daily`, running a small script that shells out to `pg_dump $DATABASE_URL | gzip | aws s3 cp - s3://... ` pointed at R2's S3-compatible endpoint using R2 API credentials (Cloudflare R2 exposes an S3-compatible API, avoiding a separate backup-specific SDK).
- 1Password Terraform provider: `infra/secrets.tf` declares `data "onepassword_item"` lookups feeding `vercel_project_environment_variable.value` and `cloudflare_...` resource secret fields, so `terraform plan/apply` in CI runs under `op run --env-file=... -- terraform apply` with a 1Password Service Account token supplied as the only long-lived credential CI itself needs to hold.
- DR drill workflow (`.github/workflows/dr-drill.yml`): creates a throwaway Neon project via Terraform in a temporary workspace, restores the latest R2 backup object into it, runs `pnpm test:integration` (from ADR-0015) pointed at the restored database's connection string as `DATABASE_URL`, tears down the throwaway project, and posts results via a Slack/Discord webhook.
- Domain/DNS: Cloudflare is also the DNS provider for `agentics.org` subdomains used by this platform (`volunteer.agentics.org`, `staging.volunteer.agentics.org`), managed via `cloudflare_record` Terraform resources pointing at Vercel's provided CNAME targets, with Vercel's domain-verification TXT records also Terraform-managed to avoid manual DNS drift.
