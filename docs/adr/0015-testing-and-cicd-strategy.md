# ADR-0015: Testing and CI/CD Strategy

## Status
Accepted — 2026-08-10

## Context
The Volunteer Portal is a commercial-grade production platform, not a scaffold — it handles hour-approval workflows that feed grant reporting (real financial/compliance consequences per ADR-0014's grant-reporting anonymization design), GDPR consent and DSAR flows with legal exposure if broken, a points/badge/leaderboard gamification ledger, a video training library, and moderated social features. The modular-monolith architecture (one Postgres schema per bounded context, cross-context integration only via transactional outbox + graphile-worker) means correctness bugs at schema boundaries — an outbox event never drained, a duplicate side effect from at-least-once delivery — are a distinct failure class from bugs inside a single schema's logic, and both need coverage.

The canonical stack fixes the testing tools (Vitest, Playwright, contract tests for the public REST API) and the deployment target (Vercel + Neon/Supabase + Cloudflare). What's undecided is: which checks gate a merge to `main`, what the environment/branch topology looks like, and what coverage is actually required — not as a percentage target, but as a concrete list of flows that must have integration-level (not just unit-level) tests before they can be called production-ready. The research's day-one checklist explicitly calls out hour-approval, consent/DSAR, and audit-trail correctness as the highest-stakes flows in the system.

## Decision
Adopt a four-layer test pyramid — unit, integration, contract, e2e-smoke — enforced by required GitHub Actions checks on every PR into `main`, with Vercel preview deployments providing a fifth, manual-verification layer per PR.

### Test layers
1. **Unit (Vitest)** — pure functions and isolated modules: the `can(subject, action, resource)` RBAC policy module, points/badge rule evaluation, retention-policy date math, Zod validation schemas at API boundaries. No database, no network. Run on every push, < 60s total.
2. **Integration (Vitest + a real Postgres instance)** — exercises Prisma against an actual Postgres (via `testcontainers` spinning up a disposable Postgres 16 container per test run, matching the Neon/Supabase production major version), including multi-schema transactions, the outbox-write-then-drain cycle (graphile-worker run in test mode against the same container), and RLS/permission boundaries. This is where cross-schema event-driven correctness is actually verified — a unit test cannot prove an outbox event is drained and applied correctly on the consuming side.
3. **Contract tests (Vitest + a schema-diff tool)** — the public REST API under `/api/v1` is OpenAPI-documented (per the canonical stack); contract tests validate that actual route handler responses conform to the published OpenAPI schema (using `express-openapi-validator`-style response validation adapted for Next.js route handlers, or `openapi-response-validator` run against captured responses in Vitest). These run against the same integration-test Postgres container. A breaking response-shape change fails CI even if the handler's own unit/integration tests pass, catching accidental public-API breakage that internal tRPC callers wouldn't surface.
4. **E2E smoke (Playwright)** — a small, deliberately narrow set of full-browser flows against a deployed Vercel preview: sign up → age gate → email verify → log in; browse opportunities → sign up for a shift; submit hours → (as a second seeded staff user) approve hours; watch a training video to completion → certificate issued; submit a DSAR export request → receive the email. "Smoke" is intentional — these are expensive and flaky-prone; deep flow coverage lives in the integration layer, not here.

### Required CI checks (branch protection on `main`)
All of the following are required status checks; none can be skipped or force-merged without repo-admin override, and repo-admin override usage is itself audit-logged via GitHub's branch protection audit log:
- `lint` — ESLint + Prettier check, no auto-fix in CI.
- `typecheck` — `tsc --noEmit` across the full workspace (Turborepo/pnpm workspace boundaries respected — see Implementation Notes).
- `test:unit` — Vitest unit suite.
- `test:integration` — Vitest integration suite against testcontainers Postgres.
- `test:contract` — OpenAPI response-shape validation.
- `e2e:smoke` — Playwright smoke suite against a Vercel preview deployment URL for the PR (runs after the preview deploy check succeeds, using Vercel's deployment-ready GitHub check as a dependency).
- `prisma:migrate-dry-run` — every migration in `prisma/migrations/` is applied to a fresh **shadow database** (a disposable Postgres created per-CI-run, distinct from the testcontainers instance used for integration tests, mirroring `prisma migrate diff --from-empty` / `prisma migrate deploy --dry-run` semantics) to catch migrations that fail outside a developer's local DB state, plus a check that no migration file has been edited after being merged (Prisma migration immutability).
- `build` — `next build` must succeed (catches type errors in edge cases `tsc --noEmit` in isolation can miss, e.g. serialization boundary issues).

A PR cannot merge to `main` unless every check above is green. There is no "merge with failing tests + follow-up ticket" path for these checks; if a check is flaky, the fix is to de-flake it, not to bypass it.

### Branch / environment strategy
- **`main`** is always deployable and maps to the **production** Vercel environment and production Neon/Supabase project.
- **`staging`** branch maps to a persistent **staging** Vercel environment with its own Neon/Supabase project (seeded with realistic but synthetic data, never a production data copy — consistent with GDPR data-minimization; no real volunteer PII in non-production environments). Merges to `staging` happen from `main` after a production-candidate is validated, or feature branches can be promoted to staging manually for stakeholder review before merge to `main`.
- **`dev`** is not a long-lived branch; local development uses `docker compose up` (Postgres + graphile-worker locally) or the testcontainers setup directly. There is no shared "dev" cloud environment — feature branches get Vercel **preview deployments** instead, which serves the same purpose with less drift risk.
- **Every PR** gets an automatic Vercel preview deployment, each with its own ephemeral Neon branch database (Neon's branching feature creates a copy-on-write branch of the staging schema+seed data per PR, torn down on PR close) — this means preview environments have real, isolated Postgres instances, not mocks, so manual QA on a preview link exercises the full stack including migrations.
- Environment promotion is strictly `preview → staging → production`; no branch skips staging for anything larger than a documentation or config-only change (those may go preview → production directly with reviewer sign-off, since they carry no schema/migration risk).

### Required coverage before a feature is "production-ready"
Coverage is not a blanket percentage target (an 80% line-coverage number is a weak proxy for the flows that actually matter here). Instead, the following flows are named as **mandatory integration-test surface** — a PR touching these must include or extend integration tests, and PR review explicitly checks for this before approval:
- **Hour-logging and approval workflow**: submit → pending → approve/reject → immutable-once-approved state transition, including the negative case (attempting to mutate an already-approved hour entry must fail at the DB/application layer, not just be discouraged by UI).
- **Consent record writes and reads** (ADR-0014): granting, revoking, and reading "current consent per purpose," including the append-only invariant (no update-in-place ever occurs).
- **DSAR export and erase jobs**: full pipeline test running the actual graphile-worker job against a testcontainers Postgres seeded with a realistic multi-schema fixture (hour entries, community posts, training progress, consent records) — asserting the export bundle contains everything and the erase job correctly anonymizes vs. hard-deletes per the documented split. This is the single highest-consequence job in the system (irreversible data mutation) and must never ship on unit-test confidence alone.
- **Audit log writes**: every privileged-action code path (hour approval, role grant, DSAR completion, moderation action) has an integration test asserting an `admin.audit_log` row is created with the correct `actor_id`, `action`, and `resource_id` — verified through the real outbox-drain path, not by mocking `recordAuditEvent`.
- **RBAC policy module (`can()`)**: integration tests (not just unit tests on the pure function) verifying that API routes actually enforce it — a route-level test attempting a forbidden action as an under-privileged role must receive a 403, exercised through the real tRPC/REST middleware stack.
- **Role-assignment scoping**: a chapter-scoped role must not grant access outside that chapter — tested with at least two chapters and cross-chapter access-denial assertions.

Unit tests are required everywhere else as the default bar (any new pure logic, validation schema, or utility function ships with unit tests), but the above list is what separates "has tests" from "production-ready."

## Consequences
### Positive
- Testcontainers-based integration tests catch the exact class of bug this architecture is most exposed to — cross-schema outbox/event-drain correctness — that unit tests structurally cannot see.
- Contract tests make the public `/api/v1` a real, enforced contract rather than an aspirational OpenAPI doc that drifts from actual handler behavior.
- Naming mandatory integration-test surfaces explicitly (rather than a coverage percentage) directs testing effort at the flows with real financial/legal/data-integrity consequences, and gives reviewers a concrete checklist instead of a vague "needs more tests."
- Neon branch-per-preview means every PR is manually reviewable against a real, isolated database with real migrations applied — catching integration issues before merge, not after.

### Negative / Trade-offs
- Testcontainers integration tests are slower and heavier than pure unit tests (container startup, real Postgres) — CI wall-clock time for `test:integration` will be materially longer than `test:unit`. Mitigated by running integration and e2e-smoke checks in parallel with lint/typecheck/unit rather than sequentially, and by scoping integration tests to the mandatory-coverage list plus schema-boundary logic rather than duplicating every unit test at the integration layer.
- Neon branch-per-PR databases add a per-PR cost and a small amount of CI complexity (branch creation/teardown as a GitHub Action step) versus a single shared staging DB. Accepted because the alternative — a shared mutable staging DB that many concurrent PRs write against — produces flaky, non-reproducible test failures that cost more engineering time than the branching mechanism.
- Mandating integration tests (not just unit) for six named flows raises the bar for shipping changes to those areas specifically, which will feel slower for small tweaks (e.g., a copy change in the DSAR email). This is intentional friction on genuinely high-consequence code paths, not blanket policy.
- E2E smoke suite depends on Vercel preview deploy completing first, adding a sequential dependency in the otherwise-parallel CI graph. Mitigated by keeping the smoke suite deliberately small (under 10 flows) so this stage stays fast.

## Alternatives Considered
- **Coverage-percentage gate (e.g., "80% line coverage required to merge") instead of named mandatory flows.** Rejected: percentage coverage is trivially gameable (testing getters/setters inflates the number while ignoring the hour-approval state machine) and doesn't map to the research's explicit finding that hour records, consent, and audit trails are the highest-stakes correctness surfaces. A named checklist reviewers can actually verify is more effective than a number.
- **Mocking Prisma/Postgres in "integration" tests instead of testcontainers.** Rejected: the entire point of the integration layer here is to catch cross-schema outbox-drain bugs and real constraint/transaction behavior (e.g., the no-cross-schema-FK rule, unique constraints, row-level anonymization correctness). A mocked ORM layer cannot exercise any of that and would just be a slower unit test with false confidence.
- **A single shared long-lived staging database for all PR review** instead of per-PR Neon branches. Rejected: concurrent PRs would corrupt each other's test fixtures and manual QA state, producing exactly the kind of flaky non-reproducible failures the team has the least capacity to debug. Neon's copy-on-write branching makes per-PR isolation nearly free in storage cost.
- **Running e2e (Playwright) as the primary correctness net, minimizing integration tests** (a common shortcut for small teams). Rejected: e2e suites are slow and flaky at scale, and the research's compliance-critical flows (DSAR erasure correctness, audit log completeness) are better and more cheaply verified by asserting directly against database state after a job run than by driving a browser through a UI that only indirectly reflects that state.

## Implementation Notes
- Monorepo layout assumed: pnpm workspaces + Turborepo (`turbo.json` pipeline defines `lint`, `typecheck`, `test:unit`, `test:integration`, `build` as cacheable tasks so unaffected packages skip re-run on unrelated PRs).
- `vitest.config.ts` splits `unit` and `integration` via separate `vitest workspace` projects (`vitest.workspace.ts`) so `pnpm test:unit` and `pnpm test:integration` can run independently and in parallel CI jobs.
- Integration test bootstrap: `tests/integration/setup.ts` uses `@testcontainers/postgresql` to start a `postgres:16` container, runs `prisma migrate deploy` against it, then runs `graphile-worker`'s schema install (`graphile_worker.migrate()`) so outbox-drain tests have a real job queue.
- Example mandatory-coverage test file locations: `apps/web/src/server/volunteering/__tests__/hourApproval.integration.test.ts`, `apps/worker/src/jobs/__tests__/dsarExportAll.integration.test.ts`, `apps/worker/src/jobs/__tests__/dsarEraseSubject.integration.test.ts`, `packages/audit/__tests__/auditLogWriter.integration.test.ts`, `apps/web/src/server/rbac/__tests__/can.integration.test.ts`.
- Contract tests: `tests/contract/openapi.test.ts` loads `openapi/v1.yaml` (the source-of-truth OpenAPI doc, generated from Zod schemas via `zod-to-openapi` to prevent doc/code drift) and validates a fixture set of real route handler responses against it using `ajv` compiled from the OpenAPI schema.
- GitHub Actions workflow file: `.github/workflows/ci.yml`, jobs `lint`, `typecheck`, `test-unit`, `test-integration`, `test-contract`, `prisma-migrate-dry-run`, `build` run in parallel where dependency-free; `e2e-smoke` depends on the Vercel deployment-ready check via `actions/github-script` polling the Vercel Deployments API for the PR's preview URL before invoking `playwright test --config=playwright.smoke.config.ts`.
- Branch protection on `main` configured via repo settings (or Terraform's `github_branch_protection` resource, consistent with ADR-0016's IaC-everything approach) listing all seven checks as required, `required_approving_review_count = 1`, and `enforce_admins = true` so even repo admins cannot bypass — an explicit choice to make override always an audited, deliberate branch-protection-setting change rather than a routine merge button.
- Neon branch-per-PR wired via the official `neondatabase/create-branch-action` GitHub Action, invoked on PR open: branch created, `DATABASE_URL` injected into the Vercel preview deployment's environment via Vercel's GitHub integration, branch deleted on PR close via `neondatabase/delete-branch-action`.
